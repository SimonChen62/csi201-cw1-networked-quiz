# CSI201 服务端网络层设计

> 版本说明（2026-10-28）：本文件从清理前备份恢复，保留为网络层设计参考；下面的接口与阶段编号属于历史计划。当前教学已推进至阶段 6：JSON 换行协议、多客户端线程、连接登记及关闭流程；实际接口和运行方法以 Codes/README.md 与源代码为准。旧版 JsonLineBuffer 实现已备份到项目外。当前 8 项测试在本机 Python 3.12 中通过；Docker 引擎尚未运行，当前版本仍需在老师镜像中复测。

## 目的

本设计说明成员 A 负责的服务端网络部分。网络层需要接受多个原生 TCP 客户端，从 TCP 字节流中还原以换行结尾的 JSON 消息，把完整请求交给业务代码，并把响应发回正确的客户端。

## 作业限制

- 使用 Python 3.12 标准库和原生 `socket`。
- 客户端和服务端都只能使用命令行。
- 不使用 `socketserver`、第三方包或高级服务器框架。
- 服务端接受 `--host`、`--port`、`--questions` 参数；完整验证题库后才监听，并且监听成功后才打印 `SERVER_READY`。
- 只有服务端可以读取题库文件。
- 集成完整系统后，至少支持 10 个连接中的客户端和 2 个互相独立的房间。
- 正确处理 TCP 分片和粘包，不能把一次 `recv()` 当成一条消息。
- 题目结束前不能向客户端发送正确答案。

## 设计方案

采用小组已经确定的 `threading` 方案。主线程负责接受新连接，每个客户端由一个处理线程负责。每个处理线程拥有自己的 socket 和接收缓冲区，因此不同客户端的字节不会混在一起。

协议模块提供两个简单接口：

```python
encode_message(message) -> bytes
extract_messages(buffer) -> (messages, remaining_buffer)
```

消息使用 UTF-8 编码的 JSON 对象，并以 `\n` 结尾。网络处理线程把解析后的对象交给分发函数；以后房间事件和比赛事件也可以通过对应客户端的发送通道主动推送。会话、房间、分数等共享状态由业务模块负责，并在那里使用锁保护；成员 A 负责连接生命周期和网络缓冲区。

## 分阶段实现顺序

1. 学习并测试 JSON 编码，以及从字节缓冲区提取完整的换行 JSON 消息。
2. 增加多线程服务端，让多个客户端同时连接，而且每个客户端使用独立缓冲区。
3. 增加错误 JSON、断线清理和业务分发接口。
4. 接入启动参数、题库验证接口、`SERVER_READY` 和 Ctrl+C 优雅关闭。
5. 在老师提供的 Docker 环境中验证成对客户端/服务端流程和并发行为。

每一步都采用“一个行为、一个测试、一个最小实现”的方式。第一步不实现房间、计分或题库业务。

## 第一步的接口

`Codes/protocol.py` 将提供：

```python
encode_message(message: dict[str, object]) -> bytes
extract_messages(buffer: bytes) -> tuple[list[dict[str, object]], bytes]
```

`extract_messages` 只移除完整的换行帧，并把尚未完整到达的尾部字节原样返回。空输入返回空消息列表。无效 UTF-8、错误 JSON，或解析后不是 JSON 对象时，抛出 `ValueError`。

## 验证方式

第一步使用 `unittest` 验证：编码后的消息能还原、消息被拆成多次接收时仍能解析、一次收到多条消息时能分别解析，以及不完整尾部能被保留。之后再增加多客户端、错误输入、断线、启动和关闭测试。最终课程证据必须在老师提供的 Docker 环境中产生；本机 Python 测试只能用于开发。
