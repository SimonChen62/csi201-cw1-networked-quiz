# Implemented application-layer protocol (v3 integration)

Version: 2026-11-15. This records the implemented protocol and team-selected rules. The coursework appendix is informative; the compulsory question-bank schema remains authoritative. Group review of this implementation is still required.

## 1. Transport and envelopes

Raw TCP, UTF-8, one JSON object followed by LF per message. Maximum JSON payload is 65,536 bytes excluding LF. A receive buffer retains incomplete tails and extracts every complete frame; one recv is not one message. Non-object roots, invalid UTF-8/JSON and nonstandard NaN/Infinity constants are rejected. Parser recursion errors become protocol errors.

Requests carry a string request_id generated by the client, starting from "1" on each connection. The server returns it unchanged. Identity comes from the source session, not the request_id. Invalid frames use request_id=null.

~~~json
{"type":"answer","request_id":"12","room_id":"R1","question_id":"NET001","choice":"B"}
{"type":"response","request_id":"12","ok":true,"data":{"accepted":true}}
{"type":"response","request_id":"12","ok":false,"error":{"code":"DUPLICATE_ANSWER","message":"only the first answer is accepted"}}
{"type":"event","event":"question_result","data":{"room_id":"R1","question_id":"NET001","answer":"B","scores":{"u1":100,"u2":0}}}
~~~

Success and failure both use type=response; ok distinguishes them. Events use type=event and have no request_id. A result may arrive before the corresponding ordinary answer/start acknowledgement because timer events run concurrently; the client matches replies by ID and protects current room/question state.

## 2. Requests

Fields below are alongside type/request_id. Success values are inside data.

| Type | Fields | Success data |
| --- | --- | --- |
| hello | user_id, name | user_id, name |
| list_quizzes | none | quizzes: public quiz list |
| list_rooms | none | rooms: joinable WAITING rooms |
| create_room | quiz_id | room: ROOM |
| join_room | room_id | room: ROOM |
| inspect_room | room_id | room: ROOM |
| ready | room_id, ready (boolean) | room: ROOM |
| start_game | room_id | empty object; question event follows or precedes reply |
| answer | room_id, question_id, choice (A/B/C/D) | accepted: true |
| leave_room | room_id | empty object |
| quit | none | bye: true; identity/seat released, then client closes connection |
| echo | text | text; development diagnostic |

Only hello, echo and quit are available before login. Active user IDs are unique. A session logs in once. IDs are 1–64 printable characters without surrounding whitespace; display names are trimmed, nonblank and at most 64 printable characters. Repeated display names are allowed.

PLAYER contains user_id, display_name, ready, score. ROOM contains room_id, quiz_id, host_user_id, state and players. State is WAITING/RUNNING/FINISHED. List-room records contain room_id, quiz_id, host_user_id, state and player_count. Public quiz records contain exactly quiz_id, title, description and question_count.

~~~json
{"type":"response","request_id":"3","ok":true,"data":{"room":{"room_id":"R1","quiz_id":"network-basics","host_user_id":"u1","state":"WAITING","players":[{"user_id":"u1","display_name":"Alice","ready":false,"score":0}]}}}
~~~

## 3. Events

| Event | Data |
| --- | --- |
| room_update | ROOM directly (not another room wrapper) |
| question | room_id, question_id, index, text, options, time_limit, points |
| question_result | room_id, question_id, answer, scores (user_id → integer) |
| leaderboard | room_id, leaderboard (rank, user_id, display_name, score) |

index is zero-based. Every room event carries room_id. Public question events contain no answer/correct field; answers appear only after closure. Client state rejects foreign-room events and stale question results. Locally synthesized server_shutdown is raised on EOF/network failure; normal server shutdown closes sockets rather than guaranteeing a wire shutdown notification.

## 4. Room and match lifecycle

One user belongs to at most one room. WAITING rooms may be joined. The server can move a user between waiting rooms; the CLI intentionally asks the user to leave first. Only the host may start, with at least two players and all current players ready. Reservation happens under the lobby lock before engine startup so no player can join or alter readiness in the startup gap.

The host passes to the lexicographically smallest remaining ID on leave/disconnect. Empty rooms are deleted. FINISHED rooms cannot restart and are not listed as joinable; users leave and create a new room. Leaving during play removes the player from the set of active answerers. A disconnected player's previously earned score remains in the final ranking.

Each match copies its quiz questions and owns its room lock, monotonic deadline, answers, scores, wake/stop events and timer thread. The first valid current-question answer before the deadline is retained; duplicates do not overwrite it. Closure occurs at the deadline or when every remaining connected player has answered. Correct answers add the configured points, wrong/missing answers add zero. The next question keeps file order. Equal final scores are ordered by user_id.

## 5. Failure behaviour

| Code | Meaning |
| --- | --- |
| MALFORMED_MESSAGE | Invalid UTF-8/JSON, non-object root or parser failure |
| MESSAGE_TOO_LARGE | Frame exceeds limit; offending connection is closed |
| INVALID_MESSAGE | Missing/wrong field, invalid identity or wrong current question ID |
| UNKNOWN_COMMAND | Unsupported request type |
| NOT_AUTHENTICATED | Login is required |
| DUPLICATE_USER | Active ID already used; existing user remains connected |
| QUIZ_NOT_FOUND / ROOM_NOT_FOUND | Unknown quiz / room |
| NOT_IN_ROOM / NOT_HOST | Membership / host check failed |
| NOT_ALL_READY | Fewer than two players or at least one unready player |
| ALREADY_STARTED | Room cannot accept this action after start reservation |
| INVALID_CHOICE | Choice is not A/B/C/D |
| LATE_ANSWER | No active question or the current deadline has passed |
| DUPLICATE_ANSWER | This player's first answer already exists |
| SERVER_SHUTDOWN | Business layer or match is stopping |
| INTERNAL_ERROR | Unexpected business/encoding failure |

An old question ID submitted after the next question opens returns INVALID_MESSAGE; this is a rejected stale submission, never a new answer. Business errors preserve the connection. An oversized frame, EOF or socket failure closes only that session. Failed broadcasts close the affected connection and continue to other recipients.

## 6. Threads, synchronization and shutdown

Server: accept loop → one worker per client; each connection has a receive buffer, send lock and idempotent close guard. Accepted sockets use a 1-second blocking-operation timeout. Idle receive timeouts continue waiting; send failure closes the connection.

Lobby: one reentrant lock protects user/session/room tables; room match state uses that room's lock. Lock acquisition is lobby then room. Network sends occur outside these locks. Engine timer and client request threads can run concurrently; ordinary replies and events share the session send lock.

Client: one receive thread demultiplexes responses and events. A request worker handles blocking connect/request calls; an input reader forwards terminal input; the CLI loop consumes input, results and events. ClientState updates occur under a reentrant lock and snapshots are deep copies.

On server SIGINT, accept stops; the lobby rejects further work and signals match stop events; network shutdown closes sockets and waits for connection cleanup; the lobby then joins tracked timer workers, including matches whose rooms were emptied. EOF disconnects clients waiting for input. The server emits no fabricated score/result for an interrupted match.

## 7. Boundaries

The implementation does not provide authentication, encryption, reconnect/resume, persistence or connection quotas. A timeout does not establish whether a state-changing request executed; the client does not automatically resend. Use inspect/players to refresh room state. Concurrency tests cover the recorded scenarios, not every possible scheduling order or arbitrary hostile load.
